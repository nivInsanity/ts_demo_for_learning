# Module 11 · `unknown`, assertions and `satisfies`

> **Files** `tasks.ts` (edit) · `tasks.test.ts` (do not edit)
> **Run** `npx vitest run src/m11-type-safety` · `npm run typecheck`

## Why this module exists

Every module before this one assumed the data matched the types. It does not.
JSON from an API, a YAML config someone hand-edited, a fixture file, a
response from a service that shipped a breaking change on Friday — none of it
is checked by the compiler, because the compiler was not there when it
arrived.

That boundary is where QA earns its keep, and it is exactly where most
TypeScript codebases give up and write `as ApiResponse`.

## `any` vs `unknown` vs `never`

| | Means | You can |
|---|---|---|
| `any` | "stop checking" | everything, including the wrong thing |
| `unknown` | "I do not know yet" | nothing, until you narrow it |
| `never` | "this cannot happen" | nothing, ever |

`unknown` is `any` with the safety on. It costs you one narrowing step and
buys you every mistake caught. `JSON.parse` returns `any`, which is why the
first thing task 11.1 does is force it to `unknown`.

## A type assertion is not a check

```ts
const config = JSON.parse(raw) as AppConfig;
```

Zero runtime code is generated by `as`. Nothing is validated, nothing is
converted. It is a note to the compiler saying "trust me". When you are wrong,
the type system keeps reporting the fiction for the rest of the program, and
the crash happens hundreds of lines from the cause.

Assertions are legitimate in exactly one shape: immediately after the check
that makes them true.

```ts
if (typeof value === 'object' && value !== null && !Array.isArray(value)) {
  return value as Record<string, unknown>;   // fine — we just proved it
}
```

The same goes for `!`. `page.owner!.email` says "I know this is not null".
If you *know*, prove it with a check. If you do not, you have written a
future incident.

## `satisfies`

```ts
const ENVIRONMENTS: Record<string, EnvConfig> = { local: {...}, prod: {...} };
//    ^ values checked, keys widened to `string`. `ENVIRONMENTS.prodd` compiles.

const ENVIRONMENTS = { local: {...}, prod: {...} } satisfies Record<string, EnvConfig>;
//    ^ values checked, keys stay 'local' | 'prod'.
```

`satisfies` validates a value against a type without replacing what was
inferred. For config objects, lookup tables and fixtures it is almost always
what you actually wanted.

## Where real projects draw the line

Hand-written validators are fine for three fields. For a real API contract,
a schema library (zod, valibot, typebox) derives the TypeScript type *and*
the runtime check from one declaration, so they cannot disagree. Doing it by
hand once, as in task 11.5, is what makes it obvious why `as ApiResponse` is
not a lighter-weight version of the same idea — it is a different idea that
checks nothing.

## Vocabulary

`unknown`, `any`, `never`, `type assertion`, `non-null assertion`,
`type predicate`, `satisfies`, `optional chaining`, `nullish coalescing`,
`boundary validation`.
